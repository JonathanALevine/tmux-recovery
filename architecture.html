Product definition

Install a command; stop thinking about tmux recovery

tmux-recovery should feel like a normal developer CLI. A user installs it globally, runs one setup command, and receives guarded automatic saves, boot or login restoration, health diagnostics, and safe process-aware recovery. 

brew install JonathanALevine/tap/tmux-recovery
tmux-recovery setup
tmux-recovery

The user should not need to understand TPM, tmux-resurrect's internal scripts, status-line scheduling, systemd unit syntax, launchd plist syntax, lock files, bootstrap sessions, or SQLite queries. Those are implementation details owned by the product.

Core product boundary: tmux-resurrect remains the snapshot and reconstruction engine. tmux-recovery becomes the installable application that owns dependency provisioning, lifecycle policy, service integration, safety, and user experience.

Who it serves

Users and primary use cases

Single-machine developer

Wants sessions, panes, paths, and everyday tools such as htop, btop, editors, and REPLs to return after a laptop update or reboot.

Multi-host operator

Wants identical policy and commands across Linux workstations, servers, and macOS without copying personal scripts manually.

Agent-heavy workflow

Runs Codex or similar long-lived interactive tools in many panes and needs application-aware conversation restoration.

Existing resurrect user

Already has snapshots and wants automation without losing compatibility with the standard resurrect data directory.

Critical user journeys

  1. Install the CLI globally and complete guided setup.
  2. Confirm that automatic saving is active.
  3. Reboot and find the tmux workspace reconstructed.
  4. Preview which pane applications will restart, resume, or fall back to a shell.
  5. Inspect status after a failed or partial restoration.
  6. Upgrade the CLI without losing snapshots or service configuration.
  7. Disable or uninstall automation without deleting user state.

Boundaries

Scope and deliberate non-goals

In scope for v1

  • One cohesive native application with headless CLI commands, stable JSON output, and a Bonsai_term TUI.
  • Managed tmux-resurrect dependency.
  • Safe manual, timer, startup, and shutdown actions.
  • systemd user services and macOS LaunchAgents.
  • Snapshot inspection and validation.
  • Conservative generic restart for approved pane applications.
  • Declarative user rules for additional executables and fixed restart commands.
  • Application-aware resume adapters, with Codex as the first advanced adapter.
  • Migration from common resurrect/continuum installations.
  • Precompiled release archives, a Homebrew tap, and a checksum-verifying installer.

Not in scope for v1

  • Keeping live processes alive through a reboot.
  • Checkpointing or recreating arbitrary process memory, open sockets, file descriptors, or kernel state.
  • Automatically replaying every captured command line.
  • Synchronizing snapshots between machines.
  • Replacing tmux, tmuxp, or tmuxinator.
  • General dotfile management.
  • Remote fleet orchestration from a central controller.
  • Windows-native tmux support.
  • Encrypted cloud backup of pane contents.
  • A long-running proprietary daemon.

Non-functional requirements

  • NFR-01: core service execution must not depend on an interactive shell profile.
  • NFR-02: normal headless commands should start in well under 100 ms on supported hardware.
  • NFR-03: save and restore mutations must be serialized across all triggers.
  • NFR-04: installation and repair must be idempotent.
  • NFR-05: uninstall must preserve snapshots unless purge is explicitly requested.
  • NFR-06: no telemetry or network communication after installation by default.
  • NFR-07: release artifacts must be reproducible enough to verify provenance and checksums.
  • NFR-08: supported service behavior must remain functional on tmux 2.7 through current tmux.
  • NFR-09: configuration must be declarative data, never sourced executable code.
  • NFR-10: failures must leave tmux attachable and the last-good snapshot intact.
  • NFR-11: UI selection and expansion state must use stable typed resource identities, never labels, tree positions, or rendered paths.
  • NFR-12: the TUI tree is a projection; presentation state must not become the canonical workspace or snapshot representation.

Architecture decision record ADR-003

OCaml is the accepted implementation language

The entire application—domain model, headless command interface, orchestration, platform adapters, and interactive TUI—will be written in OCaml. Production releases are native executables built by OxCaml's ocamlopt toolchain. The user does not install OCaml, opam, Dune, OxCaml, Node, or npm.

Decision: ADR-003 was accepted on 2026-07-20 and supersedes ADR-001's Go selection and ADR-002's npm-first delivery model. Bonsai_term makes the TUI a first-class product surface while allowing the headless CLI and UI to share typed domain values and application services in one native executable.

Why one OCaml application

  • Recovery plans, snapshot state, safety decisions, and UI state use the same algebraic data types instead of an IPC schema between two languages.
  • Bonsai_term provides declarative composition, incremental rendering, and terminal screenshot expect tests.
  • Pure domain modules remain independent of the terminal, filesystem, Async scheduler, and platform APIs.
  • Native compilation produces a standalone executable with the OCaml runtime included.
  • The product remains a normal headless CLI under systemd and launchd; the TUI is an adapter, not the core.

Toolchain policy

  • The compiler is a pinned OxCaml switch, initially based on the supported OCaml 5.2 OxCaml release line required by Bonsai_term.
  • Dune is the sole build orchestrator; dune-project is the source of package metadata and generates the opam file.
  • The project commits exact dependency constraints and a reproducible source manifest; CI never follows unpinned development branches.
  • Release artifacts use native compilation. Bytecode artifacts and ocamlrun are never shipped.
  • Compiler, Dune, Bonsai_term, Core, Async, Notty, and SQLite upgrades are tested as explicit dependency changes.
  • New runtime dependencies require a record of purpose, license, maintenance state, transitive weight, C linkage, and release impact.

Concurrency and cancellation model

  • The executable starts the Async scheduler once at the composition root; pure domain modules do not depend on Async.
  • Commands are short-lived jobs. No background fiber owns durable state after a command completes.
  • Save, restore, setup, migration, and repair acquire the same cross-process operation lock before mutation.
  • Read-only diagnostics may run concurrently through a bounded set of deferred jobs.
  • Every subprocess has explicit argv, environment, working directory, process-group ownership, timeout, and cancellation behavior.
  • Signal handling requests structured cancellation, terminates owned process groups, and waits for cleanup before choosing an exit code.

Error and transaction model

  • Expected failure is represented by typed variants carrying operation and resource context; exceptions are reserved for violated programmer invariants or library boundaries.
  • Application services return explicit result values for configuration, unavailable dependency, lock contention, invalid snapshot, unsupported provider schema, cancellation, and partial restore.
  • The CLI and TUI translate the same error value into human text, stable JSON, or an interactive recovery action.
  • Mutating commands build a plan, validate preconditions, request approval where appropriate, apply steps, verify postconditions, and roll back reversible steps in reverse order.
  • Atomic replacement uses a same-directory temporary file, permissions, flush, rename, and directory synchronization where supported.
  • Rollback failure is retained alongside the original error; neither presentation surface may hide residual state.

OCaml distribution proof before product scaffolding

  1. Build a disposable Bonsai_term application with the pinned public OxCaml/opam dependency set.
  2. Produce native macOS arm64/x64 and Linux amd64 executables on matching CI runners.
  3. Build Linux on an AlmaLinux 8-compatible glibc baseline and run the artifact on alma, c3p0, Arch, and current Ubuntu without opam.
  4. Vendor and statically link SQLite; prove read-only synthetic Codex queries without the SQLite CLI or a dynamic libsqlite3.
  5. Prove signal propagation, Async cancellation, file locking, and child process-group cleanup.
  6. Prove macOS and Linux foreground-process inspection without parsing captured text as shell syntax.
  7. Prove embedded resurrect extraction, checksum validation, and invocation by absolute path.
  8. Package the same binary through a release archive, Homebrew tap, and verified installer.
  9. Record artifact size, startup time, dynamic dependencies, toolchain source manifest, and release duration before implementation authorization.

Architecture decision record ADR-004

Install and distribution architecture

The unit of distribution is a versioned release archive containing a precompiled native executable, shell completions, a man page, license notices, and build metadata. Every friendly package channel installs the exact same tested artifact rather than rebuilding an independent variant. 

# Preferred on macOS and on machines already using Homebrew
brew install JonathanALevine/tap/tmux-recovery

# Portable user-local install for macOS and Linux
curl -fsSL https://github.com/JonathanALevine/tmux-recovery/releases/latest/download/install.sh | sh

tmux-recovery setup
tmux-recovery
Decision: npm is not required and is not a v1 dependency. It adds a Node-based launcher and four registry packages without improving the native runtime. GitHub release archives are canonical, Homebrew is the preferred managed experience, and the installer provides a package-manager-independent path. An npm wrapper may be added later only if demand justifies maintaining it.

  • Archives are produced once in CI, checksummed, signed, attested, and smoke-tested before any package channel is updated.
  • The Homebrew tap and installer reference immutable versioned URLs and expected SHA-256 values.
  • The installer accepts --version, --prefix, and a download-only mode; it never activates services.
  • Offline installation is unpack-and-copy and requires no compiler or package manager.

Install must not equal activation

Every channel only installs files. Homebrew, the verified installer, opam, and a future npm wrapper must not edit tmux configuration, start a timer, create a LaunchAgent, enable systemd units, or inspect personal snapshots. Those actions belong to an explicit tmux-recovery setup transaction.

Stable service binary

User services cannot safely depend on a package manager's shell initialization or versioned Cellar path. During setup, the native executable installs an atomic service copy under a stable user-owned path: 

~/.local/share/tmux-recovery/
└── bin/
    ├── 1.0.0/tmux-recovery
    └── current -> 1.0.0

systemd and launchd invoke the stable current binary. Running tmux-recovery setup --sync after any package upgrade installs the new service binary atomically and retains the prior version for rollback. doctor warns when the interactive executable and service copy differ.

Upgrade and uninstall contract

  • brew upgrade tmux-recovery, rerunning the versioned installer, or replacing the direct binary upgrades the interactive executable.
  • tmux-recovery setup --sync validates and advances the service binary.
  • Automatic background self-update is out of scope.
  • tmux-recovery uninstall disables services and removes managed integration but preserves snapshots.
  • tmux-recovery uninstall --purge may remove configuration and application state after an explicit confirmation.
  • Removing the package-manager copy does not silently remove an active service copy; explicit product uninstall remains the safe lifecycle path.

Automation behavior

  • Interactive setup prompts before enabling services.
  • setup --yes accepts recommended defaults for automated installs.
  • Recommended defaults enable the built-in conservative catalog, not newly invented rules or replay-all behavior.
  • setup --dry-run --json emits a machine-readable change plan.
  • Setup is idempotent and may be rerun for upgrades or repairs.
  • A failed setup rolls back files changed in the current transaction.
  • Package installation alone never performs setup implicitly.

Hard dependency policy

tmux is a system package and is not silently installed because doing so may require administrator privileges. If tmux is missing, setup stops and prints the appropriate package-manager command. Bash is required by the managed resurrect engine and is normally available on supported macOS and Linux systems.

Logical design

System architecture

Install channels

Canonical release archives, Homebrew tap, verified installer, and optional ecosystem packages.

Presentation adapters

Bonsai_term TUI plus headless human and JSON commands. Both call the same typed application services.

Application and domain

Recovery plans, invariants, transactions, locking policy, configuration, diagnostics, and migrations independent of presentation.

Platform adapters

systemd user services, launchd LaunchAgents, terminal bootstrap behavior, stable paths, and platform-specific locks.

Managed engine

A pinned, attributed tmux-resurrect distribution extracted from the CLI's embedded assets and invoked through a controlled boundary.

tmux and processes

The live tmux server, sessions, panes, shells, and explicitly supported application adapters such as Codex.

OCaml dependency direction

  • bin/main.ml constructs concrete modules, starts Async, installs signal handling, selects CLI or TUI presentation, and maps the final result to one exit code.
  • presentation_cli owns commands, help, prompts, and human/JSON rendering; presentation_tui owns Bonsai components and local interaction state. Neither owns recovery policy.
  • application owns use cases such as save, restore, setup, doctor, migrate, and service management.
  • domain owns plans, invariants, snapshot summaries, operation results, recovery types, and typed errors without Unix, Async, Bonsai, or SQLite dependencies.
  • Application services receive narrow first-class module implementations for clocks, locks, commands, tmux, storage, and providers.
  • Adapters cannot import presentation modules or each other; platform selection is confined to the composition root and adapter implementations.

Canonical workspace model: normalized graph

The user experiences tmux as a tree, but the canonical domain value is a normalized graph. A tmux window may be linked into more than one session, so copying complete windows beneath sessions would duplicate identity and eventually allow contradictory state. Sessions therefore own ordered window links; links reference canonical windows; windows own panes; and each pane may identify one foreground application as its recovery target. 

type workspace_source =
  | Live
  | Snapshot of Snapshot_id.t

type workspace = {
  source : workspace_source;
  server : Server.t;
  sessions : Session.t Session_id.Map.t;
  windows : Window.t Window_id.Map.t;
  window_links : Window_link.t list;
  panes : Pane.t Pane_id.Map.t;
}

type pane = {
  id : Pane_id.t;
  window_id : Window_id.t;
  index : int;
  cwd : Path.t;
  tty : Tty.t option;
  shell : Shell.t;
  application : Application_instance.t option;
}

Application_instance describes the foreground recovery target—not every descendant process. It records normalized executable identity, validated arguments, working directory, allowed environment evidence, adapter identity, and recoverability metadata. A diagnostic process tree may be retained separately, but it does not become the default navigation hierarchy or imply that every subprocess can be restored.

Workspace graph invariants

RelationshipInvariant
Workspace sourceEvery graph is explicitly live or belongs to exactly one immutable snapshot.
Session → window linkA session owns an ordered set of links; index and active state belong to the link, not the shared window.
Window link → windowEvery link resolves to one canonical window. The same window may be linked from multiple sessions without copying it.
Window → paneEvery pane belongs to exactly one window and has a unique index within that window.
Pane → applicationA pane has zero or one foreground recovery target. An absent target means a usable shell fallback, not a missing pane.
IdentityTyped IDs and workspace source define identity. Names, titles, indexes, and rendered tree paths are mutable presentation attributes.
ValidationDangling links, duplicate indexes, impossible active selections, and cross-snapshot references are rejected before planning or rendering.
Tree/graph boundary: application services return a validated workspace graph. The TUI projects that graph into a tree of selectable pages. CLI and JSON callers consume the graph and plans directly and never depend on navigation nodes.

Composition roots

One production composition root wires real filesystems, command execution, clocks, locks, tmux, managed resurrect, service managers, and provider adapters. Tests construct application services directly with narrow fakes. Dependencies are passed explicitly; there are no mutable package globals, hidden singleton configuration, or service locator.

No core daemon

The service manager supplies scheduling. Save and restore are short-lived CLI invocations. A resident daemon is unnecessary unless a future feature requires event streaming or remote control, neither of which belongs in v1.

Dependency ownership

tmux-resurrect should be managed, pinned, and replaceable

Requiring users to install TPM and then install a compatible resurrect checkout would undermine the "install one CLI" promise. The default v1 mode should therefore bundle a reviewed upstream resurrect release as an embedded dependency.

Managed engine model

  1. The native release embeds an exact upstream tmux-resurrect version and license notice.
  2. Setup extracts it under ~/.local/share/tmux-recovery/engines/resurrect/<version>.
  3. The CLI calls the extracted save and restore scripts by absolute path.
  4. Managed mode disables resurrect's native process replay; the application layer applies the validated process manifest only after layout restoration.
  5. Snapshots remain in the standard XDG resurrect location for interoperability.
  6. Engine upgrades ship with tmux-recovery releases and pass compatibility tests.
  7. Advanced users may configure an external resurrect path, but managed mode is the supported default.

tmux integration

tmux-recovery does not need TPM to call resurrect. Setup generates a small tmux configuration containing recovery options and keybindings, then adds one reversible managed source line to the active tmux config: 

# >>> tmux-recovery managed block >>>
source-file ~/.config/tmux-recovery/tmux.conf
# <<< tmux-recovery managed block <<<

The generated file binds manual save and restore actions to the stable service binary and supplies resurrect options. Existing user-managed resurrect installations are detected and either adopted explicitly or left untouched; setup must never create two competing automatic save systems. Managed settings also prevent upstream @resurrect-processes rules from bypassing the application's restart policy.

Global interface rules

  • --json returns versioned machine-readable output.
  • --dry-run is available on mutating configuration and service commands.
  • --quiet suppresses successful human output for service use.
  • --verbose reveals diagnostic decisions but still redacts sensitive command content.
  • --config selects an alternate configuration file.
  • --socket selects a non-default tmux socket for advanced users.
  • No interactive prompt occurs when standard input is not a terminal unless explicitly requested.
  • The TUI calls application services directly; it never scrapes human CLI output or invokes the executable recursively.
  • Every mutating TUI action displays the same typed plan and validation used by --dry-run before applying it.

Tree-shaped navigation and page routing

The primary TUI is a tree navigator paired with a selected detail page. Every visible node carries a typed Page_ref and can therefore become the current page. Nodes never embed mutable domain records; they resolve their references against the current validated workspace, snapshot, plan, or service model. 

type workspace_ref =
  | Live
  | Snapshot of Snapshot_id.t

Projection and interaction rules

  • The same projection function renders live state and any saved snapshot; the workspace source in each reference prevents accidental cross-source lookup.
  • A recovery plan is an overlay keyed by pane identity. It annotates the workspace tree rather than constructing a second contradictory topology.
  • Recovery_plan is a stable page route; recomputing the current plan replaces page data without changing navigation identity or losing selection.
  • A window linked into multiple sessions appears beneath each session with a shared marker, but every occurrence resolves to the same canonical window.
  • Expansion state and selection are sets of stable page references. Refreshing labels, indexes, badges, or process observations does not move the user's selection.
  • If a live resource disappears, selection moves to its nearest surviving ancestor and the page explains that the resource ended.
  • Tree generation is deterministic: sessions, links, panes, snapshots, and badges have explicit stable sort orders so expect-test output cannot drift.
  • Large trees are incrementally rendered and may lazily construct closed descendants, while counts and warnings still come from one consistent workspace observation.
  • Wide terminals show navigation and page side by side. Narrow terminals show one surface at a time with an explicit back action; both modes preserve the same Page_ref.
  • Keyboard navigation supports next/previous visible node, parent/child, expand/collapse, page focus, search, and help without assigning recovery actions to bare navigation keys.

State machine A

Safe save lifecycle

1

Resolve

Load typed configuration, locate tmux, the managed engine, state paths, service identity, and the selected socket without shell-profile assumptions.

2

Lock

Acquire the machine-local lifecycle lock. Manual, keybinding, timer, and shutdown saves share the same lock namespace as restore.

3

Gate

Exit successfully when no tmux server exists, only the bootstrap session exists, or a restore transaction has not committed.

4

Separate timestamps

Ensure the generated resurrect filename differs from the prior locked save second, preventing same-name rotation and dangling last links.

5

Capture

Inspect each pane's foreground process tree, classify its recovery action, then invoke the managed engine with a controlled environment.

6

Validate

Confirm that last resolves to a readable snapshot containing at least one real pane, optional pane archives are structurally valid, and every manifest record maps to one saved pane.

7

Commit

Atomically commit the snapshot-bound process manifest and last-save metadata, then emit a concise structured event. A safe no-op returns success.

State machine B

Deterministic restore lifecycle

1

Select and validate

Resolve latest or requested snapshot, reject dangling or bootstrap-only state, and verify compatibility before changing tmux.

2

Create context

If no tmux server exists, create one temporary detached restore-bootstrap session to provide the engine context.

3

Arm guard

Write an incomplete-restore marker before reconstructing state. Scheduled saves refuse to run while it is armed.

4

Restore layout

Recreate sessions, windows, shell panes, paths, layouts, focus, and optional scrollback with native resurrect process replay disabled.

5

Recover approved applications

Apply the saved process plan after required terminal capabilities and working directories are ready: restart ordinary tools, invoke resume adapters, and leave unmatched panes at a shell.

6

Clean bootstrap

Remove the temporary session only after at least one real session exists.

7

Commit or degrade safely

Clear the guard on success. If process restoration fails, retain reconstructed layouts and report a recoverable partial state.

Application restoration

Recover pane applications by capability

After a reboot, the original process no longer exists. tmux-recovery can create a new process in the reconstructed pane, but it can recover internal application state only when that application persists a session, history, or resume identifier. The product must say restart when it means restart and reserve resume for application-aware recovery.

Recovery classBehaviorExamplesState fidelity
shellRecreate the pane and working directory, then leave the user's shell ready.Unknown or disallowed processLayout and path only
restartStart a new approved executable using fixed or validated arguments.htop, btop, top, man, lessNew application instance
restart-cleanReopen an interactive tool while explicitly discarding volatile state.bare python, python3, ipythonHistory files may survive; variables and interpreter memory do not
resumeValidate application-owned persistent state and invoke a dedicated adapter.Codex conversation, Vim/Neovim sessionApplication-defined
blockedDo not replay; report why and fall back to a shell.sudo, arbitrary scripts, destructive commands, unsupported remote sessionsNone
“Any app” means any explicitly described restartable app, not arbitrary process checkpointing. tmux-recovery does not recreate process memory, Python objects, open network connections, file descriptors, kernel state, or an instruction that was executing during the save.

Default behavior

  • A built-in conservative catalog restarts common terminal monitors, pagers, and approved editor commands.
  • htop and btop are built-in restart profiles and normally return automatically.
  • A bare interactive Python or IPython command may use restart-clean; a Python script is blocked unless the user creates a specific rule.
  • Unmatched applications always fall back to a shell in the saved working directory.
  • No mode equivalent to tmux-resurrect's dangerous :all: replay is exposed.
  • Setup previews detected foreground applications and the policy that would apply, but package installation never approves processes.

Generic restart rule contract

  • Detect: combine tmux's pane PID, current-command and pane-TTY formats with the platform process table, then identify the foreground process group without assuming the immediate child is the user-visible application.
  • Match: compare a normalized executable path or basename plus structural conditions such as “interactive, no script argument.”
  • Capture: retain only the executable, structurally captured and approved arguments, working directory, selected non-secret environment keys, and the rule identifier.
  • Validate: require the executable and working directory to exist and re-evaluate the rule against current policy before launch.
  • Launch: use an argv array and an explicit environment; never evaluate a captured command with sh -c.
  • Redact: omit or mask tokens, credentials, URLs with user information, and rule-defined sensitive arguments in snapshots and output.
  • Degrade: leave an ordinary shell and report an actionable warning when any condition fails.

Platform process inspection

  • Linux reads structured process data from /proc, including NUL-delimited argv where permitted.
  • macOS uses a dedicated platform inspector for executable path and argument vectors; it does not parse human-formatted ps output as shell syntax.
  • The normalized observation contains PID relationships, foreground group, executable path, argv vector, working directory, and only policy-approved environment keys.
  • If exact argv is unavailable, only a fixed rule command may restart the application; tmux-recovery never guesses quoting by splitting a display string.
  • Permission-denied process fields reduce fidelity and produce a shell fallback rather than weakening policy.

Application-aware adapter contract

  • Detect: decide whether a live pane belongs to the adapter.
  • Capture: derive the smallest stable resume record, not an opaque process dump.
  • Validate: confirm identifiers, paths, versions, and provider state still exist.
  • Render: produce a typed launch request using approved arguments.
  • Describe fidelity: state exactly what returns and what cannot return.
  • Degrade: fall back to a clean application start or shell when exact resume is impossible.

Managed-engine bridge

The managed tmux-resurrect engine reconstructs sessions, panes, layouts, and paths with its native program replay disabled. tmux-recovery then applies its validated process manifest to those fresh panes. It launches a hidden, versioned dispatcher in the pane; the dispatcher replaces itself with the approved target executable so the application directly owns the pane's terminal.

Launch actions target only panes created by the current restore transaction and still running the expected bootstrap shell. A repeated restore never respawns a pane that a user or another process has already occupied.

This sequencing prevents upstream command strings from bypassing application policy. A compatibility shim may delegate from resurrect back to the stable CLI, but it contains only opaque snapshot and pane identifiers— never SQL, captured arguments, shell pipelines, or matching logic.

SQLite boundary

SQLite is not tmux-recovery's snapshot store. It is a read-only provider detail used to associate a running Codex process or working directory with a conversation thread. Because the SQLite command is absent on some observed hosts, the adapter should use an embedded read-only SQLite library rather than require sqlite3.

Schema isolation

  • All references to Codex database filenames and table schemas live inside the Codex adapter package.
  • The adapter probes known schema versions and returns an explicit unsupported-schema result.
  • Core save and restore behavior remains functional when the adapter breaks or Codex is absent.
  • Tests use synthetic databases and never copy real conversation data.
  • A future public Codex session API should replace direct database inspection when available.
Dangerous flags: --dangerously-bypass-approvals-and-sandbox must never be introduced silently. It requires explicit TOML opt-in, setup confirmation, a status warning, and redaction-aware logging.

Native scheduling

Background services

Linux systemd user mode

  • Restore oneshot service at user-session start.
  • Save oneshot service called by a timer.
  • Ten-minute default interval with small randomized delay.
  • Best-effort save before tmux-recovery-managed tmux shutdown.
  • User journal for logs.
  • Optional documented lingering for boot-before-login servers; never enabled with sudo automatically.

macOS launchd mode

  • Login restore LaunchAgent.
  • Periodic save LaunchAgent.
  • Absolute stable binary and log paths.
  • Terminal-bootstrap mode when required by macOS privacy permissions.
  • No sleeping forever-loop process.
  • Logout save is best effort; periodic snapshots remain the primary guarantee.

Service installation invariant

Service definitions contain only platform scheduling and calls to the stable native CLI. They do not duplicate save guards, restore logic, provider queries, or path discovery.

Configuration rules

  • Unknown keys are errors by default, preventing silent misspellings.
  • Configuration has an explicit schema version and migrations.
  • Precedence is compiled defaults, configuration file, documented environment path overrides, then explicit CLI flags.
  • Hostnames do not select behavior implicitly; profiles select capabilities.
  • Secrets do not belong in the configuration.
  • Environment variables may override configuration and state paths for testing; lifecycle policy is never inferred implicitly from the environment.
  • Process commands are argv arrays or built-in action names; configuration never contains sourced shell fragments.
  • processes plan validates rules against live panes or a snapshot without launching anything.
  • config validate performs all checks without contacting the network.

Snapshot format

v1 intentionally retains tmux-resurrect's timestamped tab-separated text snapshots, last symlink, and optional pane_contents.tar.gz. tmux-recovery maintains a versioned process manifest for validation, trigger history, pane classifications, rule identifiers, redacted launch records, and adapter resume data. It never rewrites the upstream snapshot format.

  • Each manifest records the exact snapshot basename and content hash; a mismatch disables process recovery.
  • The manifest commits atomically only after the resurrect snapshot passes validation.
  • Manifest files are mode 0600 because even redacted process metadata can reveal sensitive paths and workflows.
  • A legacy snapshot without a manifest receives a newly synthesized conservative plan; captured full commands are never trusted automatically.
  • Normal uninstall preserves process manifests with snapshots. Explicit purge may remove them after confirmation.

Recovery principles

  • Never delete the last-good snapshot during a failed save.
  • Never destroy reconstructed layouts because one provider failed.
  • Never overwrite user tmux configuration without a backup.
  • Keep the prior service binary for one-version rollback.
  • Make stale restore markers diagnosable and clearable through an explicit repair command.

Trust model

Security, privacy, and supply chain

  • State directories are user-only, normally mode 0700.
  • Snapshots may contain paths, pane titles, commands, thread IDs, and terminal output.
  • Pane-content capture defaults off for new installs.
  • Application launch is policy-allowlisted; arbitrary saved commands are not trusted by default.
  • Generic restart is rule-allowlisted and uses explicit argv; no captured process string is evaluated by a shell.
  • Privilege escalation, destructive utilities, background servers, remote connections, and scripts are blocked unless a narrowly defined user rule opts in.
  • Environment capture is deny-by-default and limited to non-secret keys explicitly approved by policy.
  • Process manifests are user-only and bind to the hash of their corresponding resurrect snapshot.
  • Provider databases are opened read-only.
  • Logs redact full command lines and provider identifiers unless explicit debug mode is enabled.
  • No telemetry, analytics, or remote snapshot upload is enabled.
  • Embedded upstream code retains licenses and attribution.
  • Release archives publish checksums, signatures, provenance, a source manifest, and an SBOM.
  • The Homebrew tap and installer pin immutable release URLs and verify the expected checksum.
  • Package installation has no activation hook; user state changes require an explicit product command.

OCaml build invariants

  • Version, commit, build date, dirty state, config schema, and engine version are exposed through tmux-recovery version --json.
  • The OCaml runtime and SQLite are linked into the artifact; Linux ldd/readelf and macOS otool audits reject unexpected package-manager libraries.

Release transaction

  1. Tag one semantic version in the source repository.
  2. Recreate the pinned OxCaml switch, verify formatting and tests, and build native artifacts in platform CI jobs.
  3. Audit dynamic linkage, glibc symbols, embedded versions, licenses, and archive contents.
  4. Generate checksums, signatures, SBOM, source manifest, license bundle, and provenance.
  5. Publish immutable GitHub release artifacts as the canonical release.
  6. Run clean-machine and fleet-baseline smoke tests against the published archives.
  7. Update the Homebrew tap and installer release index only after canonical artifacts pass.
  8. Publish the opam source package when its pinned OxCaml dependency set is available.

Version compatibility

CLI, service binary, config schema, managed engine, and provider adapter versions are reported separately. A newer interactive CLI must be able to inspect and upgrade the immediately previous service version. Config migrations must be explicit and reversible when possible.

  • Domain values cross library boundaries; Bonsai nodes, command terms, SQL rows, tmux output lines, and platform records do not.
  • The canonical workspace graph lives in domain/workspace; recursive navigation nodes and Page_ref live in presentation_tui/navigation.
  • Presentation tree nodes store stable references, labels, badges, and children only. They never own copied sessions, windows, panes, application records, or recovery decisions.
  • Provider and platform adapters translate external formats at their own boundary.
  • Only the composition root knows every concrete implementation.
  • Dune library dependencies encode and test the intended direction; there are no cyclic library dependencies.
  • Functors are used only where they create a real substitution boundary; ordinary functions and first-class modules are preferred for small ports.

Migration transaction

  1. Inventory existing configs, plugins, scripts, snapshots, and services.
  2. Create a timestamped rollback bundle excluding credentials and snapshot contents unless explicitly requested.
  3. Detect continuum and duplicate timers; plan their disablement.
  4. Install tmux-recovery in parallel without activating services.
  5. Run a manual tmux-recovery save and validate compatibility.
  6. Disable legacy automation, enable tmux-recovery, and verify one timer run.
  7. Perform a controlled tmux server restart and restore.
  8. Reboot only after controlled restore passes.
  9. Retain legacy rollback definitions until the next successful reboot cycle.

Architecture log

Recorded decisions and unresolved questions

Recorded decisions

  1. The product is one standalone native application. It exposes a Bonsai_term TUI and headless CLI; a personal script repository is not the intended user experience.
  2. Release archives are canonical. Homebrew and the verified installer install those artifacts; npm is optional and deferred.
  3. Install and activation are separate. Package installation never edits config or starts services.
  4. tmux-resurrect remains the engine. tmux-recovery manages a pinned upstream copy instead of requiring TPM.
  5. Native service managers own scheduling. v1 has no core resident daemon.
  6. State remains local. Fleet machines share releases and policy, not snapshots.
  7. Process recovery is tiered. Each pane becomes shell fallback, approved restart, application-aware resume, or blocked.
  8. Ordinary applications use declarative restart rules. A compiled adapter is required only for application-owned resume state.
  9. Arbitrary snapshot commands are never trusted. There is no restore-all mode or implicit shell evaluation.
  10. Fidelity is part of the contract. A clean Python REPL restart must not be presented as restoration of variables or interpreter memory.
  11. OCaml is the accepted whole-application language. ADR-003 supersedes ADR-001's prior Go decision.
  12. Bonsai_term is the accepted TUI framework. The public OxCaml toolchain and dependency set are pinned and proven before product scaffolding.
  13. The canonical workspace is a normalized graph. Sessions reference canonical windows through ordered window links; windows own panes; panes optionally identify one foreground recovery target.
  14. The TUI is a tree-shaped projection of that graph. Every node routes through a typed page reference, and recovery plans annotate panes rather than duplicating topology.
  15. SQLite is statically included in release artifacts. It remains read-only and replaceable behind the Codex adapter boundary.
  16. The canonical product and command name is tmux-recovery.

Open questions requiring review

  • Minimum supported macOS release and Linux baseline.
  • Whether Linux arm64 is part of v1 or the first minor release.
  • Whether the pinned Bonsai_term/OxCaml combination remains stable enough after the distribution proof or requires a versioned compatibility fork.
  • Whether sqlite3-ocaml can consume the vendored static amalgamation unchanged or needs a minimal maintained build patch.
  • Whether the managed resurrect dependency tracks releases, commits, or a maintained compatibility patch set.
  • Whether setup should enable recommended services under --yes or require a distinct service enable.
  • Whether terminal-bootstrap remains necessary after a macOS permissions spike.
  • How much snapshot detail snapshots show exposes by default.
  • Whether external third-party process adapters are supported in v1 or deferred.

Release acceptance

Definition of done for a coherent v1 system

  • A new user can install with one Homebrew or verified-installer command and complete setup without manually cloning plugins.
  • The service runtime is independent of Node, OCaml tooling, package managers, and shell-profile initialization.
  • Manual, timer, and shutdown saves cannot corrupt one another.
  • A partial restore cannot replace the last-good snapshot.
  • macOS and Linux use the same native application and common lifecycle logic.
  • Platform differences are contained in tested adapters.
  • Existing resurrect snapshots remain usable without conversion.
  • htop and btop restart automatically in their reconstructed panes under the default conservative policy.
  • A configured bare Python REPL restarts cleanly and clearly reports that its in-memory namespace was not recovered.
  • Unknown or unsafe applications fall back to shells without making the overall restore unusable.
  • Users can preview and explain every pane's recovery classification without launching processes.
  • The TUI presents live state, snapshots, recovery plans, services, and doctor results using the same typed application values as the headless CLI.
  • Every visible resource node opens a typed detail page, including session, linked window, pane, and foreground application nodes.
  • Linked tmux windows remain one canonical domain object even when the navigation tree displays them beneath multiple sessions.
  • Live, snapshot, and recovery-plan trees preserve source-scoped identity, deterministic ordering, and selection across refresh.
  • Primary TUI journeys, errors, resizing, and approval flows are protected by deterministic terminal expect tests.
  • Codex restoration works without requiring the external SQLite command.
  • Release executables include the OCaml runtime and SQLite and require no target OCaml toolchain or system SQLite library.
  • OCaml library boundaries, Async cancellation, property tests, TUI expect tests, and rollback paths are enforced in CI.
  • Unsafe Codex flags are explicit, visible, and off by default.
  • Setup, upgrade, repair, rollback, disable, and uninstall are documented and tested.
  • Canonical archives, a Homebrew tap, verified installer, checksums, signatures, provenance, licenses, source manifest, and an SBOM are published.
  • mac, arch, and alma pass controlled restart and real reboot acceptance tests.
  • No core production behavior remains as an unversioned script in a user's ~/bin.
  • Failures are diagnosable through status, doctor, JSON output, and platform logs.
