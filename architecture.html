Product definition

Install a command; stop thinking about tmux recovery

tmux-recovery should feel like a normal developer CLI. A user installs it globally, runs one setup command, and receives guarded automatic saves, boot or login restoration, health diagnostics, and safe process-aware recovery. 

npm install -g tmux-recovery
tmux-recovery setup
tmux-recovery status

The user should not need to understand TPM, tmux-resurrect's internal scripts, status-line scheduling, systemd unit syntax, launchd plist syntax, lock files, bootstrap sessions, or SQLite queries. Those are implementation details owned by the product.

Core product boundary: tmux-resurrect remains the snapshot and reconstruction engine. tmux-recovery becomes the installable application that owns dependency provisioning, lifecycle policy, service integration, safety, and user experience.

Who it serves

Users and primary use cases

Single-machine developer

Wants sessions, panes, paths, and selected tools to return after a laptop update or reboot with minimal configuration.

Multi-host operator

Wants identical policy and commands across Linux workstations, servers, and macOS without copying personal scripts manually.

Agent-heavy workflow

Runs Codex or similar long-lived interactive tools in many panes and needs application-aware conversation restoration.

Existing resurrect user

Already has snapshots and wants automation without losing compatibility with the standard resurrect data directory.

Critical user journeys

  1. Install the CLI globally and complete guided setup.
  2. Confirm that automatic saving is active.
  3. Reboot and find the tmux workspace reconstructed.
  4. Inspect status after a failed or partial restoration.
  5. Upgrade the CLI without losing snapshots or service configuration.
  6. Disable or uninstall automation without deleting user state.

Boundaries

Scope and deliberate non-goals

In scope for v1

  • One cohesive CLI with human and JSON output.
  • Managed tmux-resurrect dependency.
  • Safe manual, timer, startup, and shutdown actions.
  • systemd user services and macOS LaunchAgents.
  • Snapshot inspection and validation.
  • Conservative process replay with built-in adapters.
  • Codex restoration as the first advanced adapter.
  • Migration from common resurrect/continuum installations.
  • npm-based global installation plus direct release artifacts.

Not in scope for v1

  • Keeping live processes alive through a reboot.
  • Synchronizing snapshots between machines.
  • Replacing tmux, tmuxp, or tmuxinator.
  • General dotfile management.
  • Remote fleet orchestration from a central controller.
  • Windows-native tmux support.
  • Encrypted cloud backup of pane contents.
  • A long-running proprietary daemon.

Non-functional requirements

  • NFR-01: core service execution must not depend on an interactive shell profile.
  • NFR-02: normal commands should start in well under 100 ms on supported hardware.
  • NFR-03: save and restore mutations must be serialized across all triggers.
  • NFR-04: installation and repair must be idempotent.
  • NFR-05: uninstall must preserve snapshots unless purge is explicitly requested.
  • NFR-06: no telemetry or network communication after installation by default.
  • NFR-07: release artifacts must be reproducible enough to verify provenance and checksums.
  • NFR-08: supported service behavior must remain functional on tmux 2.7 through current tmux.
  • NFR-09: configuration must be declarative data, never sourced executable code.
  • NFR-10: failures must leave tmux attachable and the last-good snapshot intact.

Architecture decision record ADR-001

Go is the accepted implementation language

The implementation language and the install channel are separate decisions. The product core will be a Go executable. npm remains the primary installer by placing that executable behind a small JavaScript launcher and platform-specific packages.

Decision: ADR-001 was accepted on 2026-07-19. Go is selected for the native CLI because tmux-recovery is primarily an orchestration, transaction, filesystem, and subprocess application. Rust remains a respected alternative, but the project values a smaller implementation burden and simpler release pipeline more than Rust's additional compile-time control.

Decision criteria

  • Target machines should not require a matching language runtime or compiler.
  • The application must supervise subprocesses, signals, locks, files, services, and terminal-oriented workflows reliably.
  • It must ship predictably for macOS arm64/x64 and Linux amd64, with Linux arm64 feasible.
  • It needs strong testing and typed configuration.
  • The Codex adapter needs read-only SQLite access even when the sqlite3 program is absent.
  • Maintenance complexity should match a small infrastructure CLI, not a kernel component.

Why Go fits this system

tmux-recovery is primarily an orchestration and policy application. It needs reliable process execution and filesystem transactions more than advanced memory control. Go provides the native artifact, explicit error handling, concurrency primitives, standard-library process control, embedded assets, and test tooling this product needs without making ownership and lifetime mechanics part of every change.

The absence of Go on a target host is irrelevant to normal use. Release artifacts are compiled in CI; target machines receive only the native executable and managed assets. No host installs Go, Node, npm, or a SQLite command in order for scheduled recovery to run.

Go toolchain policy

  • The module path is github.com/JonathanALevine/tmux-recovery.
  • The initial source language baseline is Go 1.25; CI builds with the latest patched Go 1.26 toolchain.
  • The module and CI configuration pin the intended toolchain; developers do not rely on whichever Go happens to be first on PATH.
  • Production artifacts build with CGO_ENABLED=0 unless a later ADR records a tested exception.
  • go mod tidy produces a clean module graph and go mod verify is part of release validation.
  • The race detector, fuzz tests, static analysis, and vulnerability scanning run in CI where supported.

Concurrency and cancellation model

  • The program is synchronous by default; no background worker or resident goroutine owns durable state.
  • Each command receives one root context.Context cancelled by signals or its caller.
  • Save, restore, setup, migration, and repair acquire the same process-wide operation lock before mutation.
  • Read-only diagnostics may run independent probes concurrently through a bounded group.
  • Child processes run in controlled process groups so cancellation reaches tmux-resurrect and helper processes.
  • No goroutine may outlive command shutdown; shutdown waits for owned work or reports the timeout.

Error and transaction model

  • Packages wrap errors with operation and resource context using %w; callers classify them with errors.Is and errors.As.
  • Expected failures use typed categories such as configuration, unavailable dependency, lock contention, invalid snapshot, unsupported provider schema, and partial restore.
  • Panics are reserved for impossible programmer invariants and are recovered only at the CLI boundary to produce a crash diagnostic.
  • Mutating commands build a plan, validate preconditions, print or approve the plan, apply steps, verify postconditions, and roll back reversible steps in reverse order.
  • Atomic file replacement uses a same-directory temporary file, permission setting, flush, rename, and directory synchronization where supported.
  • Rollback failure is never hidden; the result reports both the original failure and residual state.

Go architecture proof before product scaffolding

  1. Build one throwaway Go vertical slice outside the product source tree.
  2. Prove macOS arm64 and Linux amd64 CGo-free artifacts in CI.
  3. Run Linux artifact on AlmaLinux 8 and c3p0 without installing a toolchain.
  4. Prove read-only access to synthetic Codex-style SQLite data without the SQLite CLI.
  5. Prove signal propagation and lock behavior under timer/manual collision.
  6. Prove embedded resurrect extraction, checksum validation, and invocation by absolute path.
  7. Record artifact size, startup time, dependency graph, and release workflow.
  8. Amend technical details if evidence differs; Go itself remains the accepted language unless a new ADR supersedes this one.

Architecture decision record ADR-002

Install and distribution architecture

The desired primary experience is a global npm installation, similar to other modern native CLIs: 

npm install -g tmux-recovery
tmux-recovery setup

npm is the delivery channel, not necessarily the runtime. The package should select a native binary built for the user's operating system and CPU.

Recommended npm package topology

tmux-recovery
├── bin/tmux-recovery.js
└── optionalDependencies
    ├── @tmux-recovery/cli-darwin-arm64
    ├── @tmux-recovery/cli-darwin-x64
    ├── @tmux-recovery/cli-linux-x64
    └── @tmux-recovery/cli-linux-arm64

The top-level package declares the tmux-recovery executable. Its small launcher resolves the installed platform package, starts the native binary with inherited standard streams, forwards termination signals, and mirrors the native exit status. Platform packages contain no JavaScript application logic.

Why optional platform packages: installation is registry-native, supports npm, pnpm, and compatible package managers, avoids an install-time download script, and continues to work when users disable lifecycle scripts with --ignore-scripts.

Package naming

  • Preferred public command: tmux-recovery.
  • Preferred unscoped package: tmux-recovery, subject to registry availability and ownership.
  • Fallback scoped package: @tmux-recovery/cli or a maintainer-owned scope.
  • Platform packages should be scoped even if the top-level package is unscoped.

Install must not equal activation

npm install -g must only install the command. It must not edit tmux configuration, start a timer, create a LaunchAgent, enable systemd units, or inspect personal snapshots during package installation. Those actions belong to an explicit tmux-recovery setup transaction.

Stable service binary

User services cannot safely depend on an nvm, mise, pnpm, or Homebrew-initialized shell path. During setup, the native executable should install an atomic service copy under a stable user-owned path: 

~/.local/share/tmux-recovery/
└── bin/
    ├── 1.0.0/tmux-recovery
    └── current -> 1.0.0

systemd and launchd invoke the stable current binary, never Node. Running tmux-recovery setup --sync after an npm upgrade installs the new service binary atomically and retains the prior version for rollback. doctor warns when the interactive CLI and service binary differ.

Upgrade and uninstall contract

  • npm install -g tmux-recovery@latest upgrades the interactive CLI.
  • tmux-recovery setup --sync validates and advances the service binary.
  • Automatic background self-update is out of scope.
  • tmux-recovery uninstall disables services and removes managed integration but preserves snapshots.
  • tmux-recovery uninstall --purge may remove configuration and application state after an explicit confirmation.
  • Removing the npm package alone should trigger a doctor warning if services remain, but the retained service binary prevents an immediate broken boot job.

Automation behavior

  • Interactive setup prompts before enabling services.
  • setup --yes accepts recommended defaults for automated installs.
  • setup --dry-run --json emits a machine-readable change plan.
  • Setup is idempotent and may be rerun for upgrades or repairs.
  • A failed setup rolls back files changed in the current transaction.
  • Package installation alone never performs setup implicitly.

Hard dependency policy

tmux is a system package and is not silently installed because doing so may require administrator privileges. If tmux is missing, setup stops and prints the appropriate package-manager command. Bash is required by the managed resurrect engine and is normally available on supported macOS and Linux systems.

Logical design

System architecture

Install channels

npm launcher and platform packages, release archives, and optional Homebrew distribution.

Native CLI

Commands, typed configuration, transaction planning, locking, lifecycle policy, diagnostics, structured output, and migrations.

Platform adapters

systemd user services, launchd LaunchAgents, terminal bootstrap behavior, stable paths, and platform-specific locks.

Managed engine

A pinned, attributed tmux-resurrect distribution extracted from the CLI's embedded assets and invoked through a controlled boundary.

tmux and processes

The live tmux server, sessions, panes, shells, and explicitly supported application adapters such as Codex.

Go dependency direction

cmd/tmux-recovery
        │ composition root only
        ▼
internal/cli ─────► internal/app ─────► internal/domain
                         │                    ▲
                         │ uses ports         │ owns rules and types
                         ▼                    │
                 internal/platform ───────────┘
                 internal/providers
                 internal/engine
  • cmd/tmux-recovery constructs dependencies, installs signal handling, executes the root command, and maps the result to one exit code.
  • internal/cli owns parsing, help, prompts, and human or JSON rendering; it contains no tmux policy.
  • internal/app owns use cases such as save, restore, setup, doctor, migrate, and service management.
  • internal/domain owns plans, invariants, snapshot summaries, operation results, and provider-neutral recovery types.
  • Adapters implement small interfaces declared by the package that consumes them. A large global service container is prohibited.
  • Provider packages cannot import CLI, service-manager, or another provider package.
  • Platform-specific files use Go build constraints only at the platform boundary; common lifecycle logic has no operating-system build tags.

Composition roots

One production composition root wires real filesystems, command execution, clocks, locks, tmux, managed resurrect, service managers, and provider adapters. Tests construct application services directly with narrow fakes. Dependencies are passed explicitly; there are no mutable package globals, hidden singleton configuration, or service locator.

No core daemon

The service manager supplies scheduling. Save and restore are short-lived CLI invocations. A resident daemon is unnecessary unless a future feature requires event streaming or remote control, neither of which belongs in v1.

Dependency ownership

tmux-resurrect should be managed, pinned, and replaceable

Requiring users to install TPM and then install a compatible resurrect checkout would undermine the "install one CLI" promise. The default v1 mode should therefore bundle a reviewed upstream resurrect release as an embedded dependency.

Managed engine model

  1. The native release embeds an exact upstream tmux-resurrect version and license notice.
  2. Setup extracts it under ~/.local/share/tmux-recovery/engines/resurrect/<version>.
  3. The CLI calls the extracted save and restore scripts by absolute path.
  4. Snapshots remain in the standard XDG resurrect location for interoperability.
  5. Engine upgrades ship with tmux-recovery releases and pass compatibility tests.
  6. Advanced users may configure an external resurrect path, but managed mode is the supported default.

tmux integration

tmux-recovery does not need TPM to call resurrect. Setup generates a small tmux configuration containing recovery options and keybindings, then adds one reversible managed source line to the active tmux config: 

# >>> tmux-recovery managed block >>>
source-file ~/.config/tmux-recovery/tmux.conf
# <<< tmux-recovery managed block <<<

The generated file binds manual save and restore actions to the stable service binary and supplies resurrect options. Existing user-managed resurrect installations are detected and either adopted explicitly or left untouched; setup must never create two competing automatic save systems.

State machine A

Safe save lifecycle

1

Resolve

Load typed configuration, locate tmux, the managed engine, state paths, service identity, and the selected socket without shell-profile assumptions.

2

Lock

Acquire the machine-local lifecycle lock. Manual, keybinding, timer, and shutdown saves share the same lock namespace as restore.

3

Gate

Exit successfully when no tmux server exists, only the bootstrap session exists, or a restore transaction has not committed.

4

Separate timestamps

Ensure the generated resurrect filename differs from the prior locked save second, preventing same-name rotation and dangling last links.

5

Capture

Invoke the managed engine with a controlled environment and process-adapter configuration.

6

Validate

Confirm that last resolves to a readable snapshot containing at least one real pane and that optional pane archives are structurally valid.

7

Commit

Atomically record last-save metadata and emit a concise structured event. A safe no-op returns success.

State machine B

Deterministic restore lifecycle

1

Select and validate

Resolve latest or requested snapshot, reject dangling or bootstrap-only state, and verify compatibility before changing tmux.

2

Create context

If no tmux server exists, create one temporary detached restore-bootstrap session to provide the engine context.

3

Arm guard

Write an incomplete-restore marker before reconstructing state. Scheduled saves refuse to run while it is armed.

4

Restore layout

Recreate sessions, windows, panes, paths, layouts, focus, and optional scrollback.

5

Restore approved processes

Execute process adapters only after required terminal capabilities and working directories are ready.

6

Clean bootstrap

Remove the temporary session only after at least one real session exists.

7

Commit or degrade safely

Clear the guard on success. If process restoration fails, retain reconstructed layouts and report a recoverable partial state.

Application restoration

Process adapters must be conservative

A saved command is not automatically trusted merely because it appeared in a tmux pane. Default restoration rebuilds layout and shells. Applications restart only through explicit adapters that recognize, validate, and render safe commands.

Adapter contract

  • Detect: decide whether a live pane belongs to the adapter.
  • Capture: derive a stable minimal restoration record.
  • Validate: confirm identifiers, paths, and provider state still exist.
  • Render: produce the exact safe command to store or execute.
  • Redact: provide a status-safe summary without secrets.
  • Degrade: fall back to a shell or provider start command when exact resume is impossible.

Built-in adapters are compiled into the native CLI. The resurrect engine may require a small executable shell strategy file; setup generates that file as a compatibility shim that delegates back to the stable CLI. The shim contains no SQL, process traversal, or policy.

SQLite boundary

SQLite is not tmux-recovery's snapshot store. It is a read-only provider detail used to associate a running Codex process or working directory with a conversation thread. Because the SQLite command is absent on some observed hosts, the adapter should use an embedded read-only SQLite library rather than require sqlite3.

Schema isolation

  • All references to Codex database filenames and table schemas live inside the Codex adapter package.
  • The adapter probes known schema versions and returns an explicit unsupported-schema result.
  • Core save and restore behavior remains functional when the adapter breaks or Codex is absent.
  • Tests use synthetic databases and never copy real conversation data.
  • A future public Codex session API should replace direct database inspection when available.
Dangerous flags: --dangerously-bypass-approvals-and-sandbox must never be introduced silently. It requires explicit TOML opt-in, setup confirmation, a status warning, and redaction-aware logging.

Native scheduling

Background services

Linux systemd user mode

  • Restore oneshot service at user-session start.
  • Save oneshot service called by a timer.
  • Ten-minute default interval with small randomized delay.
  • Best-effort save before tmux-recovery-managed tmux shutdown.
  • User journal for logs.
  • Optional documented lingering for boot-before-login servers; never enabled with sudo automatically.

macOS launchd mode

  • Login restore LaunchAgent.
  • Periodic save LaunchAgent.
  • Absolute stable binary and log paths.
  • Terminal-bootstrap mode when required by macOS privacy permissions.
  • No sleeping forever-loop process.
  • Logout save is best effort; periodic snapshots remain the primary guarantee.

Service installation invariant

Service definitions contain only platform scheduling and calls to the stable native CLI. They do not duplicate save guards, restore logic, provider queries, or path discovery.

Configuration rules

  • Unknown keys are errors by default, preventing silent misspellings.
  • Configuration has an explicit schema version and migrations.
  • Precedence is compiled defaults, configuration file, documented environment path overrides, then explicit CLI flags.
  • Hostnames do not select behavior implicitly; profiles select capabilities.
  • Secrets do not belong in the configuration.
  • Environment variables may override configuration and state paths for testing; lifecycle policy is never inferred implicitly from the environment.
  • config validate performs all checks without contacting the network.

Snapshot format

v1 intentionally retains tmux-resurrect's timestamped tab-separated text snapshots, last symlink, and optional pane_contents.tar.gz. tmux-recovery may maintain a small sidecar metadata file for validation and trigger history, but it must not rewrite the upstream snapshot format.

Recovery principles

  • Never delete the last-good snapshot during a failed save.
  • Never destroy reconstructed layouts because one provider failed.
  • Never overwrite user tmux configuration without a backup.
  • Keep the prior service binary for one-version rollback.
  • Make stale restore markers diagnosable and clearable through an explicit repair command.

Trust model

Security, privacy, and supply chain

  • State directories are user-only, normally mode 0700.
  • Snapshots may contain paths, pane titles, commands, thread IDs, and terminal output.
  • Pane-content capture defaults off for new installs.
  • Process replay is adapter-allowlisted; arbitrary saved commands are not trusted by default.
  • Provider databases are opened read-only.
  • Logs redact full command lines and provider identifiers unless explicit debug mode is enabled.
  • No telemetry, analytics, or remote snapshot upload is enabled.
  • Embedded upstream code retains licenses and attribution.
  • npm and release artifacts publish checksums, provenance, and an SBOM.
  • The npm launcher verifies that it found the expected platform package; it does not download executable code at runtime.
  • Package postinstall hooks are avoided.

Distribution operations

Release engineering

Target artifacts

  • darwin/arm64
  • darwin/amd64
  • linux/amd64, CGo-free and tested on the minimum supported Linux baseline
  • linux/arm64 when CI and hardware validation are available

Go build invariants

  • Release builds use the pinned patched toolchain, CGO_ENABLED=0, -trimpath, and reproducible version metadata.
  • Version, commit, build date, dirty state, config schema, and engine version are exposed through tmux-recovery version --json.
  • No release binary dynamically depends on a system SQLite library.
  • Every platform artifact executes its version and doctor probes on a matching runner before publication.
  • Dependency licenses, govulncheck results, an SBOM, checksums, and build provenance accompany the release.

Release transaction

  1. Tag one semantic version across core and npm packages.
  2. Verify modules, format, vet, test, fuzz smoke targets, scan, and build native artifacts in platform CI jobs.
  3. Generate checksums, SBOM, license bundle, and provenance.
  4. Publish GitHub release artifacts.
  5. Publish platform npm packages.
  6. Publish the top-level npm launcher only after platform packages succeed.
  7. Run clean-machine install smoke tests from the public registry.
  8. Advance latest; use next for prereleases.

Version compatibility

CLI, service binary, config schema, managed engine, and provider adapter versions are reported separately. A newer interactive CLI must be able to inspect and upgrade the immediately previous service version. Config migrations must be explicit and reversible when possible.

This is the approved implementation shape, not application code. Unit tests and fixtures live beside their Go packages in *_test.go and testdata/; the top-level tests/integration tree is reserved for black-box tests. No public pkg/ API is planned for v1.

Package rules

  • Packages are organized around capabilities, not generic util, common, or models buckets.
  • Interfaces are declared where consumed and normally contain one to three methods.
  • Domain values cross package boundaries; Cobra commands, SQL rows, tmux output lines, and platform structs do not.
  • Provider and platform adapters translate external formats at their own boundary.
  • Only the composition root knows every concrete implementation.
  • Internal packages may later be split only when an actual dependency or test boundary requires it.

Migration transaction

  1. Inventory existing configs, plugins, scripts, snapshots, and services.
  2. Create a timestamped rollback bundle excluding credentials and snapshot contents unless explicitly requested.
  3. Detect continuum and duplicate timers; plan their disablement.
  4. Install tmux-recovery in parallel without activating services.
  5. Run a manual tmux-recovery save and validate compatibility.
  6. Disable legacy automation, enable tmux-recovery, and verify one timer run.
  7. Perform a controlled tmux server restart and restore.
  8. Reboot only after controlled restore passes.
  9. Retain legacy rollback definitions until the next successful reboot cycle.

Architecture log

Recorded decisions and unresolved questions

Recorded decisions

  1. The product is a standalone CLI. A personal script repository is not the intended user experience.
  2. npm is the primary install channel. It may launch a native binary rather than define the core runtime.
  3. Install and activation are separate. Package installation never edits config or starts services.
  4. tmux-resurrect remains the engine. tmux-recovery manages a pinned upstream copy instead of requiring TPM.
  5. Native service managers own scheduling. v1 has no core resident daemon.
  6. State remains local. Fleet machines share releases and policy, not snapshots.
  7. Process replay is allowlisted. Arbitrary snapshot commands do not receive automatic trust.
  8. Go is the accepted core language. ADR-001 was accepted on 2026-07-19.
  9. The Go core is CGo-free by default. SQLite remains replaceable behind the Codex adapter boundary.
  10. The canonical product and command name is tmux-recovery.

Open questions requiring review

  • Whether the npm package remains unscoped or uses a maintainer-owned scope if registry acquisition changes.
  • Minimum supported macOS release and Linux baseline.
  • Whether Linux arm64 is part of v1 or the first minor release.
  • Whether the initial modernc.org/sqlite candidate passes compatibility, size, and supply-chain acceptance or is replaced behind the same interface.
  • Whether the managed resurrect dependency tracks releases, commits, or a maintained compatibility patch set.
  • Whether setup should enable recommended services under --yes or require a distinct service enable.
  • Whether terminal-bootstrap remains necessary after a macOS permissions spike.
  • How much snapshot detail snapshots show exposes by default.
  • Whether external third-party process adapters are supported in v1 or deferred.

Release acceptance

Definition of done for a coherent v1 system

  • A new user can install with one npm command and complete setup without manually cloning plugins.
  • The service runtime is independent of Node and shell-profile initialization.
  • Manual, timer, and shutdown saves cannot corrupt one another.
  • A partial restore cannot replace the last-good snapshot.
  • macOS and Linux use the same CLI and common lifecycle logic.
  • Platform differences are contained in tested adapters.
  • Existing resurrect snapshots remain usable without conversion.
  • Codex restoration works without requiring the external SQLite command.
  • Release binaries are CGo-free and require no target Go toolchain or system SQLite library.
  • Go package boundaries, cancellation behavior, race checks, parser fuzzing, and rollback paths are enforced in CI.
  • Unsafe Codex flags are explicit, visible, and off by default.
  • Setup, upgrade, repair, rollback, disable, and uninstall are documented and tested.
  • npm artifacts, direct binaries, checksums, provenance, licenses, and an SBOM are published.
  • mac, arch, and alma pass controlled restart and real reboot acceptance tests.
  • No core production behavior remains as an unversioned script in a user's ~/bin.
  • Failures are diagnosable through status, doctor, JSON output, and platform logs.
