The central idea

Resurrect owns snapshots. Steward owns policy.

tmux-steward is not a tmux replacement and not a fork of tmux-resurrect. It is the operational layer that decides when saving is safe, how restoration is sequenced, which processes may be relaunched, and how the behavior is installed and observed on each operating system.

Service manager

Schedules saves and invokes startup or shutdown actions through systemd user units or macOS LaunchAgents.

tmux-steward

Applies locks, validates state, chooses a restore driver, exposes diagnostics, and dispatches process strategies.

tmux-resurrect

Serializes tmux metadata and pane contents, then reconstructs sessions, windows, panes, layouts, and selected commands.

tmux

Owns the live server, sessions, clients, windows, panes, environment, and process terminals.

Architectural rule: native service managers provide scheduling and lifecycle ownership. tmux-steward does not need a forever-running daemon for its core save and restore responsibilities.

Problem statement

Why tmux-resurrect alone was not enough

Lifecycle is external

Resurrect supplies save and restore operations, but it does not guarantee periodic saves, shutdown saves, login startup, or service-manager integration.

Generic process replay is risky

Broad restoration can restart SSH sessions, monitoring tools, servers, and unrelated Node processes. The fleet needs an explicit allowlist and application-specific strategies.

Boot is a different environment

A detached service has no normal tmux client, may have a minimal environment, and on macOS may not inherit the terminal permissions needed to reopen protected working directories.

Concurrent automation can damage state

Resurrect snapshot names have second-level resolution. Timer, manual, and shutdown saves need serialization so the last link cannot point to a removed file.

Codex needs conversation identity

Reopening a pane is insufficient. The correct working directory and Codex thread identifier must be recovered and converted into an exact codex resume command.

The fleet has multiple restore modes

macOS, ordinary Linux hosts, and Arch's palette-sensitive boot path require different drivers behind the same public command.

Continuum is not the foundation. It remains useful for many installations, but its status-line-driven scheduling and tmux-server-start restore hook do not provide enough control for this fleet's startup ordering, safety checks, and Codex behavior.

Scope

Goals and deliberate non-goals

Goals

  • One repository and one CLI for macOS and Linux.
  • Safe, serialized, unattended saves.
  • Deterministic restore after login, reboot, or tmux failure.
  • Codex-aware restoration without broad process replay.
  • Capability-based restore drivers instead of hostname branches.
  • Idempotent install, upgrade, repair, and uninstall operations.
  • Useful status and doctor output before touching live state.
  • Tests that reproduce the races and detached-client problems already encountered.

Non-goals

  • Replacing tmux-resurrect's snapshot format.
  • Keeping processes alive through a machine reboot.
  • Synchronizing snapshots between hosts.
  • Versioning terminal output, Codex databases, or conversation state.
  • Managing general tmux appearance or keybindings.
  • Becoming a declarative workspace launcher like tmuxp or tmuxinator.
  • Starting arbitrary saved commands without an explicit process policy.

Component model

Small modules with explicit responsibilities

CLI

Command router

Parses commands, loads strict configuration, selects the platform adapter, and returns stable exit codes.

Core

Save controller

Acquires the lock, rejects unsafe intermediate states, waits out filename collisions, and invokes resurrect quietly.

Core

Restore controller

Validates the last snapshot, creates bootstrap context when necessary, executes a driver, and records completion.

Adapter

Platform service

Renders and manages systemd user units or generated launchd plists without leaking platform details into core logic.

Adapter

Restore driver

Implements direct, staged-palette, or terminal-bootstrap restoration behind one interface.

Extension

Process strategy

Translates a live or saved application process into a safe restart command. Codex is the first supported extension.

Installer

Integration manager

Installs command links, tmux snippets, strategy links, profiles, and service definitions idempotently.

Diagnostics

Doctor

Checks dependencies, permissions, plugin revisions, configuration, service state, snapshot validity, and repair actions.

Migration

Legacy importer

Detects the current loose scripts and service definitions, compares behavior, and performs a reversible cutover.

Lifecycle A

Safe save sequence

1

Normalize the environment

Resolve tmux, the resurrect plugin, state paths, runtime paths, and the active configuration without relying on an interactive shell profile.

2

Acquire the cross-platform save lock

Use flock on Linux and lockf on macOS through one lock abstraction. All manual, timer, and shutdown saves share it.

3

Apply safety gates

Exit successfully if no tmux server exists, only the bootstrap session exists, or restoration is in a deliberately incomplete phase.

4

Avoid timestamp collisions

Wait until the wall-clock second differs from the previous locked save rather than sleeping unconditionally. This preserves resurrect's last symlink invariant.

5

Invoke tmux-resurrect

Run its save script in quiet mode, allowing resurrect to produce tab-separated metadata, rotate old snapshots, and create pane-content archives.

6

Validate and report

Confirm that last resolves to a readable snapshot containing at least one real pane, then emit a concise structured log entry.

Important: a timer save that finds nothing safe to save is a successful no-op, not an operational failure.

Lifecycle B

Deterministic restore sequence

1

Validate the candidate

Resolve last, reject missing or dangling snapshots, and ensure the file contains a pane outside restore-bootstrap.

2

Create bootstrap context if needed

Start one detached restore-bootstrap session only when no tmux server is running. This gives resurrect the server context it expects.

3

Arm the incomplete-state guard

Mark restoration as active before reconstructing anything. Scheduled and shutdown saves must refuse to overwrite the last-good snapshot during this interval.

4

Execute the selected restore driver

The direct driver restores once. The staged driver restores layouts with process replay disabled, then launches approved processes after terminal capabilities are ready.

5

Remove bootstrap state

Kill the temporary session only after at least one real restored session exists. Never let it become a saved workspace.

6

Commit restoration

Clear the guard, record the driver and snapshot used, and leave the tmux server detached and attachable.

Restore drivers

Driver Use Behavior
direct Ordinary Linux and macOS environments One resurrect restore with approved process strategies enabled.
staged-palette Arch graphical startup Restore layouts first, then start Codex through a deterministic terminal-control environment.
terminal-bootstrap macOS when Terminal permissions are required Invoke the restore through Terminal.app so protected directories inherit the expected user-granted access.

Process extension

Codex-aware restoration

Codex is treated as an application adapter, not baked into the generic lifecycle controller. The adapter has two jobs: identify the correct conversation while saving and render a deterministic resume command while restoring.

Inspect pane find the child process and working directory
Resolve thread query Codex state or parse an existing resume command
Validate session confirm the thread still has persisted session material
Save command serialize exact cwd and thread ID into resurrect
Resume launch Codex only under the explicit process policy

Where SQLite fits

SQLite is an implementation detail of the Codex adapter—not the tmux-steward or tmux-resurrect storage format. The current stack reads Codex's logs_2.sqlite to associate a process with a thread and may read state_5.sqlite to find the latest unarchived thread for a working directory.

Policy decision required during implementation: the current resume command includes --dangerously-bypass-approvals-and-sandbox. Steward must never add that implicitly. It should require an explicit, prominently documented configuration value and surface the setting in doctor output.

Plugin integration seam

The Codex save-command and restore strategy files currently live inside the tmux-resurrect checkout. Versioned copies will instead live in tmux-steward. The installer will create and verify small symlinks inside the plugin's strategy directories. A plugin update that removes them is repairable with tmux-steward doctor --repair.

Native lifecycle

systemd and launchd integration

Linux: systemd user units

  • A oneshot restore service ordered with the user session.
  • A oneshot save service invoked by a user timer.
  • A ten-minute timer with explicit jitter and no dependence on tmux's status line.
  • A best-effort shutdown save before terminating the tmux server.
  • Logs available through the user journal.
  • Paths use systemd specifiers such as %h wherever possible.

macOS: LaunchAgents

  • A login restore agent using the selected restore driver.
  • A periodic save agent with a 600-second interval.
  • Generated absolute paths because launchd does not expand shell shortcuts.
  • Logs stored under the user's state or Library log directory.
  • An optional Terminal-bootstrap driver for macOS privacy permissions.
  • No daemon is kept alive merely to sleep between saves.
Same commands, different adapters: both platforms ultimately invoke tmux-steward save and tmux-steward restore. Platform files contain no duplicate lifecycle logic.

Configuration model

Strict data, not executable configuration

Configuration should use a strict KEY=VALUE format parsed by steward rather than sourced by the shell. This keeps the first implementation dependency-free while avoiding arbitrary code execution during service startup. 

# ~/.config/tmux-steward/config
SAVE_INTERVAL_SECONDS=600
RESTORE_DRIVER=direct
PROCESS_PROFILE=codex
CAPTURE_PANE_CONTENTS=1
CODEX_RESUME_MODE=thread
CODEX_BYPASS_APPROVALS=0
LOG_LEVEL=info

Precedence

  1. Built-in conservative defaults.
  2. Repository-shipped platform profile.
  3. Installed machine profile.
  4. User configuration.
  5. Explicit CLI flags for the current invocation.

Restore behavior is selected by capability profile, not inferred from a hostname inside the code. A host may choose staged-palette or terminal-bootstrap explicitly while retaining the same common core.

Operator interface

A small, predictable CLI

Command Contract
save Perform a guarded snapshot. Accept a reason such as manual, timer, or shutdown for logging.
restore Restore the latest validated snapshot through the configured driver.
status Show tmux state, last snapshot, restore phase, service state, driver, and process profile.
doctor Run read-only checks by default; optionally repair repository-owned links and generated files.
service install Render platform definitions and tmux integration without enabling them.
service enable Enable the installed user services after validation.
service disable Stop and disable steward automation without deleting snapshots.
migrate Inventory the existing loose stack, save a rollback bundle, install steward, and cut over in ordered steps.

Stable exit behavior

  • 0: completed or safe no-op.
  • 2: invalid command or configuration.
  • 3: dependency or integration problem.
  • 4: no valid snapshot available.
  • 5: tmux or resurrect operation failed.
  • 6: safety gate rejected a forced operation.

Correctness

Reliability invariants

  1. One lifecycle mutation at a time. Save and restore share a machine-local lock namespace.
  2. Never replace last-good with bootstrap-only state. A valid snapshot must contain a real pane outside the temporary session.
  3. Never save a half-restored workspace. An armed restore marker blocks timer and shutdown saves until completion or explicit recovery.
  4. Service operations are idempotent. Reinstalling or enabling twice produces the same files and service state.
  5. Uninstall does not delete user data. Snapshots, logs, and configuration are retained unless separately requested.
  6. Process relaunch is allowlisted. Shells and pane layouts may be reconstructed broadly; application commands require a named strategy.
  7. Failure remains attachable. A failed process-restore stage must leave restored tmux layouts available for inspection.
  8. No hidden cross-host authority. Each machine owns its own tmux state and can recover independently.

Safety model

Snapshots are sensitive operational data

  • State directories should be user-only, normally mode 0700.
  • Snapshots may reveal paths, commands, pane titles, thread IDs, and captured terminal output.
  • Pane-content capture remains configurable and visible in doctor output.
  • Logs must not copy full saved command lines unless debug logging is explicitly enabled.
  • SSH configuration, addresses, usernames, keys, and routing never enter this repository.
  • Generated service definitions use the current user's paths but contain no credentials.
  • Repair mode only changes files owned by tmux-steward's installation contract.
  • Dangerous Codex launch flags require explicit opt-in and a warning in status output.
tmux-resurrect captures state; it is not an encrypted backup system. Cross-machine backup, encryption, retention, and redaction would be a separate future project boundary.

Verification strategy

Test policy before fleet deployment

Static checks

  • ShellCheck for every shell entry point.
  • Formatting and executable-bit checks.
  • Generated systemd unit verification.
  • Generated plist syntax validation.
  • HTML and documentation link checks.

Unit tests

  • Strict configuration parsing.
  • Snapshot validation with synthetic fixtures.
  • Lock selection and timeout behavior.
  • Codex command parsing and SQL fallback logic.
  • Restore-driver selection and guard transitions.

Integration tests

  • Temporary isolated tmux sockets.
  • Save and restore of sessions, layouts, and pane paths.
  • Manual and timer save collision.
  • Detached save without a current client.
  • Bootstrap cleanup and incomplete-restore blocking.

Fleet acceptance

  • One canary host at a time.
  • Reboot and login verification.
  • Shutdown-save verification.
  • Codex thread-resume verification.
  • Rollback using the preserved legacy bundle.

CI should run on current Ubuntu and macOS. Older tmux compatibility, especially Alma's tmux 2.7 behavior, remains an explicit acceptance target even if hosted CI uses a newer package.

Cutover protocol per host

  1. Run inventory and save a rollback bundle of existing scripts, configs, and unit definitions.
  2. Install steward without enabling it.
  3. Run doctor and a dry-run render of services and integration links.
  4. Trigger a manual steward save and validate the new snapshot without deleting old snapshots.
  5. Disable the legacy timer or LaunchAgent.
  6. Enable steward services and verify one scheduled save.
  7. Perform a controlled tmux-server restart and restore test.
  8. Perform a reboot test only after the controlled test passes.

5

Add idempotent deployment, repair, rollback bundles, and machine-readable diagnostics.

6

Canary rollout

Migrate the local Mac first, then arch, alma, and the less-complete hosts one at a time with controlled restart and reboot tests.

Resolved design choices

Architecture decisions

  1. Keep tmux-resurrect as an external engine. Do not fork its snapshot format or duplicate reconstruction logic.
  2. Replace continuum with native service scheduling. Avoid status-line coupling and gain explicit lifecycle observability.
  3. Use a shell-first modular implementation. Preserve proven behavior and broad host compatibility before considering a language rewrite.
  4. Model special startup behavior as drivers. No hardcoded if hostname = arch branches in common logic.
  5. Make process replay opt-in. Codex is supported through a named adapter; arbitrary saved applications are not automatically trusted.
  6. Keep state local to each machine. Fleet deployment shares code and policy, not live tmux snapshots.
  7. Install first, enable separately. Rendering files is reversible; activating background behavior is an explicit later action.

Open implementation questions

  • Whether macOS can eventually use direct LaunchAgent restore without Terminal.app permissions.
  • Whether to upstream support for external tmux-resurrect strategy directories.
  • Whether the project should pin tested plugin commits or only enforce minimum compatible revisions.
  • Whether a future compiled CLI would materially improve installation enough to justify replacing shell modules.

Acceptance criteria

What “a coherent system” means

  • Every host invokes the same public CLI and shares the same common lifecycle code.
  • Platform and terminal differences are isolated behind adapters and profiles.
  • No production logic remains as an untracked, hand-edited file in ~/bin.
  • No custom strategy is maintained only inside a third-party plugin checkout.
  • A timer save, manual save, and shutdown save cannot corrupt one another.
  • A half-completed restore cannot overwrite the last known-good snapshot.
  • Codex resumes the intended thread and working directory under explicit policy.
  • Install, enable, disable, repair, upgrade, migrate, and uninstall paths are documented and tested.
  • The Mac, arch, and alma pass controlled restart and reboot acceptance tests.
  • Failures leave enough logs and status information to diagnose without reading implementation code.
First implementation milestone: reproduce the current local Mac save and restore behavior entirely from this repository, with tests and a rollback path, before changing any other fleet host.
